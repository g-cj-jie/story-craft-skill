# novel-context

## 适用边界

由 novel-leader 在每章 novel-write 和 novel-review 完成后调用。接收变动清单和审查报告，更新所有状态文件。

**必须在主会话或可靠模型（mimo-v2.5+）中执行。** glm-4-flash 等弱模型不会实际写入状态文件——它们声称更新了文件但实际未调用 write_file。历史教训：147章（52-198章）因弱模型跳过状态更新，导致状态文件冻结。

只做状态更新和归档，不写正文、不审内容。

## 执行主流程

### 步骤1：读取输入

接收本章正文、变动清单（novel-write输出）、审查报告（novel-review输出）、当前所有 state/ 文件。

### 步骤2：增量更新8个状态文件

1. **current-position.md** — 章号+1；若到达篇/卷/部边界则更新对应层级编号
2. **character-state.md** — 更新本章有变化的人物字段；连续30章未出现→标记休眠
3. **faction-state.md** — 同人物更新逻辑
4. **foreshadow-ledger.md** — 新埋伏笔追加行；已填伏笔改状态；超期告警
5. **subplot-state.md** — 更新进度%；已完成标记
6. **recent-summary.md** — 滚动更新最近3章摘要（每章≤100字）
7. **arc-brief-current.md** — 更新篇内位置和已发生关键事件
8. **critical-data-snapshot.md** — 每章强制更新：技能等级/技能点账目/随身物品/实力面板/故事时间。**此文件不受2000字限制，压缩时数值原样传递。**

### 步骤2.5：跨章一致性审查（新增）

逐项核对本章与前一章的精确数据：
1. **前章数值面板 vs 本章数值面板**：等级、技能等级、技能点、资源数量是否一致（除非章纲明确要求变化）
2. **前章关键场景设定 vs 本章对应描述**：地点、难度、幕数等背景描述是否一致
3. **前章物品清单 vs 本章涉及物品**：新增/丢失/状态变化是否在变动清单中有交代
4. **前章伏笔台账 vs 本章伏笔操作**：编号/状态/是否超期
5. **章纲规划范围 vs 本章实际范围**：地点/角色/事件级别是否超前

发现矛盾时的处置：
- 明确矛盾（如等级Lv1→Lv2无交代）→ 标记为"错误"，回报leader
- 可能为伏笔（如角色说错话但后续未解释）→ 标记为"待确认"
- 数值偏差但可解释 → 标记为"需补充说明"

输出：跨章一致性审查结果（附在上下文更新确认表之前）

### 步骤3：检查归档

人物退场/死亡、伏笔填坑（篇结束时）、子剧情完成（篇结束时）、势力覆灭→从状态文件移除，移入 `state/archive/`。

### 步骤4：边界处理

- 篇结束：归档+统计+生成新 arc-brief
- 卷结束：增加卷级摘要
- 部结束：增加部级摘要+状态转 REVIEW_PART

详见 references/boundary-handling.md。

## 输出要求

**每次执行必须输出以下两个表。** 这是验证状态更新是否真正落地的唯一凭证。

### 一、上下文更新确认表（必须）

逐文件确认更新状态。每个状态文件必须列出具体变更内容，禁止笼统写"已更新"：

| 状态文件 | 状态 | 具体变更 |
|---------|:----:|------|
| 当前位置.md | ✓/✗ | 部X卷Y篇Z章N→N+1（全局第XXX章）；或到达边界时的层级变更 |
| 人物状态.md | ✓/✗ | 列出每个有变更的人物ID+变更内容；无变更则写"无" |
| 势力状态.md | ✓/✗ | 列出每个有变更的势力ID+变更内容；无变更则写"无" |
| 伏笔台账.md | ✓/✗ | 新埋FS-XX；填坑FS-YY；推进FS-ZZ；超期告警或无 |
| 子剧情状态.md | ✓/✗ | 列出进度%变化；标记"即将完成(>80%)"或"已完成" |
| 近期摘要.md | ✓/✗ | 淘汰第N-3章摘要，新增第N章摘要 |
| 当前篇简报.md | ✓/✗ | 关键事件+1；篇内位置更新 |
| 关键数据快照.md | ✓/✗ | 技能/物品/技能点/实力/时间锚点更新情况 |
| 归档检查 | ✓/✗ | 列出归档项或写"无" |
| 风格自检 | ✓/✗ | 破折号密度(X个/千字)；时间跳跃；语气漂移；大纲对齐 |
| 连续性交叉验证 | ✓/✗ | 通过/异常项列表（参照continuity-checklist.md） |

**若任一文件标记为✗，必须附带原因和补救动作。**

### 二、进展表（必须）

整体写作进度的快照：

| 维度 | 数据 |
|------|------|
| 当前位置 | 部X/5 卷Y/8 篇Z/7 章N/18（全局第XXX章） |
| 本章字数 | X,XXX字 |
| 本篇累计 | XX,XXX字 / 目标XX,XXX-XX,XXX字（XX%） |
| 活跃伏笔 | X个待填 / X个超期（超期ID列表） |
| 活跃子剧情 | X个进行中 / X个即将完成 / X个已完成 |
| 活跃人物 | X人活跃 / X人休眠 / X人近期退场 |
| 活跃势力 | X个 |
| 风格告警 | 有/无（有则简述） |
| 连续写作章数 | 当前会话已写X章 |
| 上下文压缩包 | 已重写（下一章子Agent入参来源） |

### 三、上下文压缩包（必须）

每章后写入 `写作状态/上下文压缩包.md`。此文件是下一章 leader 组装子Agent入参的**唯一上下文来源**，效果等同于开新会话：

```markdown
# 上下文压缩包 — 第N章后

## 上一章核心要点（≤300字）
## 小说重点功能清单（世界观+人物+势力状态摘要）
## 进度清单（本篇目标+下章目标+待推进子剧情）
## 活跃钩子与伏笔（近期需填坑+进行中伏笔+下章操作）
## 最近3章摘要
## 风格告警（如有）
```

详见 novel-leader/references/context-assembly.md 的"上下文压缩机制"章节。
